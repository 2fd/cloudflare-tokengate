# Changelog

This file lists every change that users and operators can see, per release. It is for operators who upgrade a deployment and for workflow authors.

The format follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/). The project uses [Semantic Versioning](https://semver.org/). Before 1.0.0, a minor version can contain breaking changes; "Upgrade notes" lists them. The release process is in [CONTRIBUTING.md](CONTRIBUTING.md#release-process).

## [Unreleased]

First public release (0.1.0).

### Admin UI redesign

The admin UI has four sections, in this order in the sidebar: Monitoring, Service tokens, Service consumers and Users ([ADR 0019](docs/adr/0019-admin-information-architecture.md), [ADR 0022](docs/adr/0022-admin-ui-on-design-system-d.md)). Token and access duties are separate roles ([ADR 0018](docs/adr/0018-role-split-and-field-permissions.md)).

- **New URLs.** Services are at `/admin/tokens`, caller providers at `/admin/consumers` and grants at `/admin/access`. The Settings page is removed: Data retention (`/admin/retention`), Allowed hosts (`/admin/tokens/hosts`), Encryption keys (`/admin/tokens/keys`) and Sign-in (`/admin/users/sign-in`) replace it, the system status is on the Overview, and admins and owners find "Export configuration" in the account menu. An unknown admin URL shows a "Page not found" page that links to the sections; an old URL says where its page moved.
- **Page shell.** Every admin page has a skip link and a sidebar (a top bar with a Menu button on phones): the instance name and host, a health line ("Healthy", "N warnings to review" or "N problems to fix", linked to the Overview), the four sections with the pages of the open one, and an account menu with the signed-in role, the version, "Export configuration" (admins and owners), a Docs link to the section's docs, and Sign out. A strip at the top of the page names problems that stop calls, such as missing encryption keys. Owners see how many people need a decision on the Users link. The forbidden page names the roles that may make the change and who has them. The stylesheets (`ui.css` and `pages.css`, served by the Worker) meet WCAG 2.2 AA contrast in light and dark mode.
- **Operation presets.** Service templates offer named operations, for example "Post messages: POST /chat.postMessage", instead of one starter rule list. The grant form still prefills the default operations as rule text.

<!-- WP1 -->
- **Monitoring › Overview.** One page answers "is everything OK?" for the last 24 hours, 7 days or 30 days: a health panel with every alert (each with links to the objects it concerns and, for the roles that can, the fix; owners approve pending people and re-encrypt secrets in place) and every check, the four getting-started steps, request counts that link to the matching Requests list, a bar chart with a table of the numbers, "Tokens in use" (which consumer accesses can use each token, with traffic and last use), the top denied callers with "Create access" and the last 5 changes. It replaces the Dashboard and its banners.
- **Monitoring › Requests.** Time range and outcome tabs, token, consumer and reason lists, a repository field with suggestions from stored labels only, filter chips, and table cells that set filters. "Find a request" on every Monitoring page opens a record from a pasted request ID or log line. Invalid filters are dropped with a message, and the other results still show. The query parameter `service` is now `token` (no alias). A record says what to do for its reason, with links for the roles that can act, and always re-checks against the current consumer accesses (`?reevaluate=1` is gone). "Create grant from this request" is now "Give access from this request".
- **Monitoring › Audit log.** Range and category tabs, and lists of objects and people, replace the target type and free-text filters (`target_type` and `target_id` are removed; use `target=<id>`). Changes show as a Before and After table.
- **Monitoring › Data retention.** The settings are grouped, the numbers have suggestions, the sample rate is a choice of presets, and summary retention can no longer be shorter than request record retention.
- **Request log indexes.** `apps/gateway/migrations-telemetry/0001_initial.sql` gains two `request_log` indexes for the Monitoring pages (problem rows, and rows per consumer access). Local databases made before this change must be recreated: run `pnpm run setup`.
<!-- WP2 -->
- **Users › People.** "Needs your decision" lists pending people and refused sign-ins that only an owner can fix (an expired or cancelled invitation, a different Access account for a known email), each with the action that fixes it and "Dismiss". Approving is one click per role ("Approve as" Viewer, Token manager, Access manager or Admin; Owner after a confirmation). "Invite someone" makes the role button the submit, and Enter invites as Viewer. Inviting an expired or cancelled invitation's email invites it again instead of failing. Filter chips show who holds which role, a search appears above 20 people, and each row has one state button ("Reactivate", "Renew invitation", "Invite again" or "Email sign-in link") plus a "Change" disclosure with the role buttons and the other actions. Irreversible or escalating actions (reset sign-in, cancel an invitation, to or from Owner, suspending an owner) ask for confirmation; reversible ones show "Undo" in the result notice. A change made on a stale page is refused (`409`).
- **Person page** (`/admin/users/:id`): status, the same controls, the last refused sign-in, the sign-in accounts (Access user ID without the team domain), what the person changed in 30 days per category, and the account's history.
- **Users › Sign-in.** The console address to send people; the join policy as one click ("Ask an owner first", "Let them in as" a role, or "Only invited people"; elevated roles ask for confirmation); admin hosts added or removed one per submit, a pasted URL reduced to its hostname, with a one-click pin while none is set; and the login provider status.
- **Refused sign-ins are recorded** on the user they name (time and login subject, not audited, at most every 5 minutes), so owners see who tried. The sign-in problem page says so, and has its own text for an expired invitation.
- **Labels.** "Reset login" is now "Reset sign-in", "Resend invitation" is now "Renew invitation", and "Cancel invitation" deletes a user who never signed in (`user.delete`) instead of suspending it. New audit actions: `user.approve`, `user.reject`, `user.delete` and `user.dismiss_attempt` (approve and reject were `user.update`). `POST /admin/users/defaults` is replaced by `POST /admin/users/sign-in/policy` (`join_policy`).
<!-- WP3 -->
- **Service tokens: one form per type.** "Add a token" on `/admin/tokens` is an accordion with one card per template plus Custom API; a template card asks only for the secret (name, slug, description and expiry are optional and derived), and its base URL, injection, headers, timeout and check come from the template, never from the form. A whole Slack or Discord webhook URL is pasted as is. A secret with another vendor's prefix, or a URL in a card that takes none, is refused before anything is sent. GitHub can add the release-asset uploads token from the same paste. The Anthropic template now checks the key (`GET /v1/models`).
- **Service tokens: the token page.** It shows who can use the token first ("2 consumers can use this token", with chips per consumer, last use and "Give a consumer access", or a link to send to an access manager), then the secret with an inline **Replace secret** form, the proxy base URL, the destination and a Danger zone. Rotating keeps the stored destination and offers to replace the same secret in the other GitHub token. **Change destination** asks for the secret again and for the destination host also when no secret is stored. A failed submit keeps the secret for 15 minutes as a sealed draft, so "Save without a passing check" is one click ([ADR 0020](docs/adr/0020-sealed-credential-drafts.md)). An owner can allow a blocked host from the token form. Admins can delete a token together with its consumer access in one confirmed step. Testing a GitHub token saves the expiry GitHub reports.
- **Allowed hosts and Encryption keys.** Allowed hosts lists the hosts tokens and templates use to tick, plus typed others; a pasted URL becomes its host, and IPs, `localhost` and `workers.dev` are refused with the line number. Encryption keys shows each key's status and secrets, the problems with the affected tokens, and re-encryption behind a confirmation.
- **Upgrade note: token routes.** `POST /admin/tokens/:id/credential` is replaced by `POST /admin/tokens/:id/secret` (rotate, the stored destination is kept) and `POST /admin/tokens/:id/destination` (base URL and injection with the secret again). Create takes `template=<id>` (or `custom`) and the secret; the slug and name are derived when empty. A service with no stored secret now needs the destination host typed before its first secret is saved.

- **Service consumers.** "Add a consumer" asks only for what the gateway cannot derive: the organizations (GitHub) or groups (GitLab) as `name (ID)`, pasted from the `gh` or `glab` command in the hint, or the issuer (generic OIDC). The name, issuer, JWKS URI, algorithms (from discovery, generic only), token age and audience are derived. Adding a GitHub or GitLab consumer for an issuer that already has one adds the organizations to it. The consumer page has the CI snippet with the real token slugs, the tokens it can use per repository, organizations that can be added as a list and removed unless enabled accesses use them, trust settings with the confirmation shown up front, and one confirmed delete that also deletes its accesses.
- **Consumer access.** A matrix and a list show which consumers can use which tokens, with statuses as words and a "+" in each empty cell that opens the prefilled form. One form gives access: the consumer and the token are fixed when there is one, radio cards when there are a few; with no consumer yet, the consumer is added in the same submit. GitHub and GitLab accesses are built from the repository, a context (environment, branch, tag, any protected ref, release, pull request or any ref) and a protected-refs choice; "Write conditions by hand" opens a rows editor, also for generic consumers. Allowed operations are the token template's named operations and the operation sets other accesses of the token use. Expiry is never, 7, 30 or 90 days, or a day. "Copy to another repository or token" is one submit. See [docs/policies.md](docs/policies.md#structured-access-form) and [ADR 0021](docs/adr/0021-structured-consumer-access-and-labels.md).
- **Risk acceptance by selection.** A risky choice says "Risk:" in its label and choosing it accepts that risk; other warnings need the acknowledgement box, bound to the exact risks shown. The audit row records the accepted risk codes.
- **Display labels.** Repositories, organizations and groups are shown by name: the name typed with an ID is stored as a display label of the consumer (`claim_labels`), written with the save that typed it. Labels never change what an access allows. The form's suggestions come only from saved consumers and accesses, never from the request log.
- **Give access from a request.** "Give this caller access" on a denied, verified request prefills the structured form with the caller's repository, context and protected-refs state and the exact call.
- **Removed.** The condition and rule text fields, the profile chooser page, the "Step 1 of 2" grant chooser and the `?duplicate=` copy. Consumers and accesses are at `/admin/consumers` and `/admin/access`, with the new routes `POST /admin/consumers/:id/tenants` and `POST /admin/access/:id/copy`. A copy is now enabled at once.

The health checks are one collapsed line at the bottom. An empty install shows Get started first. "Find a request" is on the Overview, Requests, Audit log and Data retention pages.

- **Service tokens › list.** One primary "Add token" in the header; status quick links (now with Disabled) and a name or slug search (`?q=`); a Used by column with consumer tiles, a count link and names; 30-day request counts; and problems as callouts that name the token. The "Add a token" accordion is gone: `?open=add` redirects token writers to `/admin/tokens/new`.
- **Service tokens › Add token.** A type catalog of cards, each with a "When you save" summary, and one optional "Name and options" group. After a failed check, the summary names who rejected the secret and the card shows the upstream's answer.
- **Service tokens › token page.** An identity header with Test and one primary action ("Give a consumer access", or "Ask an access manager" by email); a relation line; a "Who can use" map capped at 3 consumers × 3 accesses, with a note and links to the matrix; secret, use, destination and Danger zone trays; and a rail with the record (with who created the token) and the latest changes. The delete dialog asks for the slug and offers "Disable instead". The missing-secret and outside-allowed-host callouts use the warning tone, the same level as the Overview alerts.
- **Allowed hosts and Encryption keys** are settings pages: read-only cards, the allowed-hosts edit in a dialog and the re-encrypt confirmation in a dialog.
- **Service consumers.** Each consumer page has a header with identity, a relation line and a rail. The consumers list shows token chips.
- **Consumer access.** The page opens on a connections map, with the last 24 hours of traffic per token, followed by the access list; the matrix is a Map | Matrix switch. A new Expired status filter and Needs-attention quick links are added. The map can focus one consumer (`?focus=`), and its "+ N more" group nodes open the matrix filtered to those consumers or tokens. The Give access form has numbered steps, a live summary rail, a repository picker with "Another repository", and a risk acceptance before the submit. The access page has a call-flow trace, a copy form, an edit disclosure and an activity and history rail. The secret state of a token reads "Secret set" or "No secret yet", no longer "credential".

#### Upgrade notes for the redesign

- **Roles and schema.** The roles `token_manager` and `access_manager`, the `claim_labels` table and `services.template_id` are part of `apps/gateway/migrations/0001_initial.sql`; there is no second migration. Local databases made before this change must be recreated: run `pnpm run setup`. `admin` keeps everything it could do before.
- **URLs.** There are no redirects from the old URLs (`/admin/services*`, `/admin/caller-providers*`, `/admin/grants*`, `/admin/settings*`). They show the "Page not found" page with a hint to the new page. Update bookmarks and links in runbooks.
- **Export schema 2.** The configuration export has `schema_version` 2. Each service has a `template_id` (the service template it was made from, or `null` for a custom service), a new `claim_labels` array holds the display labels of numeric IDs per caller provider, and `users` can have the roles `token_manager` and `access_manager`. Tools that read version 1 must accept these fields. The export never contains secrets or row IDs.

### Access rules

<!-- WP-R2 -->
- **One kind of rule per credential.** Credential access rules (boundaries) and issuer access rules are merged into one credential access rule, stored in the new `access_rules` table with `acr_` IDs. Each credential access rule applies to exactly one credential and holds its own token verification settings: issuer, profile, JWKS URI, audience, allowed algorithms, maximum token age, tenant pin and anchor claims ([ADR 0026](docs/adr/0026-global-and-credential-access-rules.md)).
- **Global access rules.** A global access rule (`gar_` IDs, same table) is a ceiling on every credential access rule of one issuer. It can limit the token settings, the identity conditions and the operations, and it never lets a workload in by itself. A request is allowed only when one credential access rule of the credential matches it and, when the caller's issuer has any global access rule, one enabled, unexpired global access rule of that issuer holds too ([I-AUTHZ-1](docs/threat-model.md#i-authz-1), [I-AUTHZ-5](docs/threat-model.md#i-authz-5)). A change that widens a ceiling needs a confirmation. The pages are at `/admin/credential-access-rules` and `/admin/global-access-rules`; `/admin/issuer-access-rules` shows the "Page not found" page with a hint to the new page.
- **403 code renamed.** The 403 code for a request that no access rule admits is now `no_matching_rule` (it was named after grants). Update callers and alerts that match the old code. The new request record reason `outside_global_rules` tells that no global access rule held; the caller still sees `no_matching_rule`.
- **Roles.** Credential managers no longer manage access rules. They can still delete a credential that has no credential access rules. Access managers manage credential access rules. Admins and Owners also manage global access rules (new permission `access_rules:global`). Every signed-in person can read global access rules.
- **Export schema 4.** The configuration export has `schema_version` 4, with the arrays `credential_access_rules` and `global_access_rules`. The `issuer_access_rules` array and the old `credential_access_rules` shape are removed.
- **Telemetry columns.** `request_log.grant_id` is now `global_access_rule_id`; the rollup key `grant_id` of `request_rollup_hourly` is now `credential_access_rule_id`; the trace field `grant_id` is now `rule_id`.
- **Upgrade note: archive stream v2.** The request-log archive uses `pipelines/request-log.v2.schema.json`, and `apps/gateway/scripts/setup-archive.sh` creates `tokengate_requests_v2` by default. An existing archive stream drops the new records silently: create the v2 stream with `scripts/setup-archive.sh` and switch the pipeline to it.
- **Upgrade note: local databases.** `apps/gateway/migrations/0001_initial.sql` and `apps/gateway/migrations-telemetry/0001_initial.sql` are changed in place. Local databases made before this change must be recreated: run `pnpm run setup`.

### Repository layout

The repository is a pnpm workspace. The Worker moved, unchanged, to `apps/gateway/` (package `@tokengate/gateway`): its code, tests, migrations, static files, `wrangler.jsonc`, `.dev.vars.example` and Worker scripts (`keyring.ts`, `check-config.sh`, `setup-archive.sh`). `docs/`, `actions/`, `pipelines/` and the repository checks stay at the root. The root scripts (`pnpm run setup`, `pnpm dev`, `pnpm run deploy`, `pnpm test`, `pnpm keyring`, …) delegate to the package, and `pnpm wrangler …` runs Wrangler in `apps/gateway`. The get-token action test is now `actions/get-token/test.sh`. See [CONTRIBUTING.md](CONTRIBUTING.md#repository-layout).

- **Upgrade note: Workers Builds.** If Workers Builds deploys your copy, set the build's root directory to `apps/gateway`. The Deploy button now points at `apps/gateway`.
- **Upgrade note: local state.** Local development files now live in the package: move `.dev.vars` to `apps/gateway/.dev.vars` and `.wrangler/` to `apps/gateway/.wrangler/`, or run `pnpm run setup` again. If your clone changes `wrangler.jsonc`, check that the merge carried your changes to `apps/gateway/wrangler.jsonc`.
- **Design system.** `packages/ui` (`@tokengate/ui`) holds design system D: one stylesheet (`src/styles/ui.css`, served at `/static/ui.<hash>.css`) and server-rendered Hono JSX components with no client JavaScript. `packages/docs` (`@tokengate/docs`) documents it under `/docs`. It is a library, not a Worker: `pnpm dev` now runs `apps/gateway/src/dev.ts`, which serves `/docs` on `localhost`, `127.0.0.1` and `[::1]` (<http://localhost:8787/docs>) and otherwise runs the production Worker. Deploys use `src/index.ts`, which never includes the docs, so `/docs` answers 404 in production ([I-DEPLOY-2](docs/threat-model.md#i-deploy-2); `apps/gateway/scripts/check-bundle.sh` checks the deployed bundle). The gateway bundles `**/*.css` as text modules (a `rules` entry in `wrangler.jsonc`). The admin UI is built on it.

### Added

- **Credential proxy.** `/proxy/<slug>/…` accepts `GET`, `HEAD`, `POST`, `PUT`, `PATCH`, `DELETE` and `OPTIONS`. The caller sends a workload identity token in `x-tokengate-token` or `Authorization: Bearer`. For `header` Injection, it can also send the token in the injected header. The gateway verifies it, checks grants, removes the token and injects the stored credential. Responses stream back. See [docs/architecture.md](docs/architecture.md).
- **Caller providers** with three profiles: `github-actions`, `gitlab-ci` and `generic` (other OIDC issuers). Each caller provider has its own audience and maximum token age, and an optional tenant pin (required on shared issuers). `generic` Caller providers also list their anchor claims. See [docs/callers/github-actions.md](docs/callers/github-actions.md), [docs/callers/gitlab-ci.md](docs/callers/gitlab-ci.md) and [docs/callers/generic-oidc.md](docs/callers/generic-oidc.md).
- **Grants** with claim conditions (`exact` and `glob`, optional negation) and rules (HTTP methods plus a path glob). Each grant can have an expiry. Trusted events per profile; any other event needs an explicit opt-in in the grant. GitHub presets for branch, tag, release, pull request and environment. See [docs/policies.md](docs/policies.md).
- **Injection kinds:** `bearer`, `header` (name and optional prefix), `basic`, `query` and `path`.
- **Service templates** for the Slack Web API, Slack incoming webhooks, Discord webhooks, OpenAI, Anthropic, the GitHub REST API and GitHub uploads. An optional verify check tests a credential when it is saved or tested. See [docs/upstreams/](docs/upstreams/).
- **Envelope encryption** of credentials with AES-256-GCM and a keyring (`TOKENGATE_KEK` or `TOKENGATE_KEYRING`). Key rotation with key check values and a rewrap action in Settings. `pnpm keyring generate` and `pnpm keyring check` generate and validate keys outside Cloudflare. See [docs/operations/key-rotation.md](docs/operations/key-rotation.md).
- **Admin UI** at `/admin`, server-rendered without client-side JavaScript: Dashboard, services, caller providers, grants, Requests, Audit log, users, Settings. "Create grant from this request" prefills a grant from a denied request record.
- **Admin sign-in through Cloudflare Access only.** The Worker verifies the Access JWT on every `/admin` request; it keeps no sessions of its own. "Sign out" goes to the Access logout endpoint. Users have the role `owner`, `admin`, `token_manager`, `access_manager` or `viewer`: token managers manage services and credentials, access managers manage caller providers and grants, and admins do both ([ADR 0018](docs/adr/0018-role-split-and-field-permissions.md)). The first person to sign in becomes owner; everyone else that Access lets in joins with the role (`viewer` by default, or any role except `owner`) and status (`active` by default, `pending` or `suspended`) that owners set on the Users page. Users have the status `invited`, `pending`, `active` or `suspended`. The Users page lists pending users apart, with one-click "Approve" and "Reject", and lets owners change each user's role and status. An owner can also invite an email with another role. For local development, `AUTH_ACCESS_DEVELOPMENT` signs in as one email, and only on requests to `localhost`, `127.0.0.1` or `[::1]`. See [ADR 0015](docs/adr/0015-cloudflare-access-only-admin-login.md).
- **Request log** in a separate D1 database (`TELEMETRY_DB`), with hourly rollups, retention settings, a sample rate for allowed requests and a row cap. Optional Queue for batched writes (`REQUEST_LOG_QUEUE`) and optional archive to R2 through Basin Pipelines (`REQUEST_ARCHIVE`, `apps/gateway/scripts/setup-archive.sh`, `pipelines/request-log.v1.schema.json`). See [docs/observability.md](docs/observability.md).
- **Audit log** of every admin change, invite link, first-owner bootstrap and first sign-in of a new user, also emitted as an `audit.event` log line for a SIEM.
- **Health endpoints:** `/healthz` (liveness, no I/O) and `/readyz` (readiness, booleans only).
- **Configuration export** (`POST /admin/export`) as deterministic JSON without secrets.
- **Optional per-Grant rate limit** through the `PROXY_RATE_LIMITER` binding.
- **Composite GitHub Action** `actions/get-token` that mints the OIDC token and installs the `tokengate-token` helper. See [actions/get-token/README.md](actions/get-token/README.md).
- **Deploy to Cloudflare** support: binding descriptions in `package.json`, `.dev.vars.example`, and `pnpm run deploy`, which applies both migrations before it deploys.
- **Upstream host allowlist in Settings.** Owners list the hosts that services may use ("Upstream hosts", audit action `settings.upstream_hosts`). Empty, the default, allows any public https host. See [docs/configuration.md](docs/configuration.md#upstream-host-allowlist).
- **Admin hosts in Settings.** `/admin` answers only on the hostnames that owners list in Settings > "Admin hosts" (audit action `settings.admin_hosts`). The first sign-in stores its hostname as the first entry. Entries are exact hostnames or `*.<domain>`. A save cannot empty the list or drop the hostname in use. See [docs/configuration.md](docs/configuration.md#admin-hosts) and [ADR 0016](docs/adr/0016-admin-hosts-in-settings.md).
- **`pnpm run setup`** copies `.dev.vars.example` to `.dev.vars` for local development. It also deletes the local D1 databases (`.wrangler/state/v3/d1`) and applies the migrations to new ones. The copy works with `pnpm dev` as is: it sets a public development key in `TOKENGATE_KEK` and `AUTH_ACCESS_DEVELOPMENT=dev@example.com`. The keyring refuses that key (`dev_placeholder_key`) unless `AUTH_ACCESS_DEVELOPMENT` is set and no Access variable is set. See [CONTRIBUTING.md](CONTRIBUTING.md#set-up) and [docs/configuration.md](docs/configuration.md#development-key).

### Security

Each item links to its invariant in [docs/threat-model.md](docs/threat-model.md).

- The Caller token never reaches the upstream. Only one compact JWS of at most 16 KiB is accepted; different tokens in different headers are rejected ([I-TOK-1](docs/threat-model.md#i-tok-1), [I-TOK-2](docs/threat-model.md#i-tok-2)).
- Tokens verify only with the exact issuer, an allowed algorithm, the caller provider's audience and a fresh `iat`. JWKS refetches are rate-gated per `jwks_uri` ([I-JWT-1](docs/threat-model.md#i-jwt-1), [I-JWT-2](docs/threat-model.md#i-jwt-2)).
- Shared issuers (`token.actions.githubusercontent.com`, `gitlab.com`) need a tenant pin on one of the profile's tenant claims (`repository_owner_id` or `enterprise_id` for GitHub, `namespace_id` for GitLab) ([I-TEN-1](docs/threat-model.md#i-ten-1)).
- Every grant must satisfy the profile's anchor rules: exact, non-negated conditions on immutable IDs or on a path-based workflow pin (`job_workflow_ref`, `ci_config_ref_uri`). This is checked at save time and at request time. A Grant that no longer satisfies them is skipped ([I-AUTHZ-2](docs/threat-model.md#i-authz-2)).
- A missing, null or non-scalar claim makes a condition false, also when it is negated ([I-AUTHZ-4](docs/threat-model.md#i-authz-4)).
- GitLab `parent_pipeline` and `pipeline` are not trusted events. A Grant must opt in to them with an exact, non-negated condition, and the UI warns when it does not also require `ref_protected` ([I-AUTHZ-3](docs/threat-model.md#i-authz-3)).
- A request without a matching grant is denied, and revocation takes effect on the next request. Rules match the path with `%2F` read both as a separator and as data. `/x/*` and `/x/**` never authorize `/x/`. Method-override query parameters (`_method`, `x-http-method-override`, `x-http-method`, `x-method-override`) are refused with `path_invalid` ([I-AUTHZ-1](docs/threat-model.md#i-authz-1)).
- The upstream URL stays on the service's base origin and base path ([I-PATH-1](docs/threat-model.md#i-path-1)).
- Caller copies of the injected header or query parameter are removed. The credential appears only in the outbound request ([I-INJ-1](docs/threat-model.md#i-inj-1)).
- Credentials are bound by AAD to the service ID, base URL and injection. They never appear in responses, logs, audit rows or the export ([I-CRED-1](docs/threat-model.md#i-cred-1), [I-CRED-2](docs/threat-model.md#i-cred-2)).
- Every keyring key is bound to `AUTH_ACCESS_TEAM_DOMAIN`, `AUTH_ACCESS_AUD` and `AUTH_ACCESS_DEVELOPMENT` with HKDF-SHA256. A change to any of them makes every stored credential impossible to decrypt, and key check values depend on them ([I-CRED-3](docs/threat-model.md#i-cred-3), [ADR 0017](docs/adr/0017-kek-bound-to-login-variables.md)).
- Redirects are returned, never followed. A `Location` under the base URL is rewritten to the gateway, one on another origin passes through, and any other is dropped. `Link` keeps only the values that rewrite to the gateway ([I-REDIR-1](docs/threat-model.md#i-redir-1)).
- Upstream response headers are filtered. A header that echoes the credential is dropped and named in `x-tokengate-redacted` ([I-RESP-1](docs/threat-model.md#i-resp-1)). Response bodies pass through unchanged.
- Base URLs are https only, checked against the upstream host allowlist (when set) when a service is saved and on every request. The allowlist is a setting that owners edit in Settings > "Upstream hosts"; empty allows any public https host, and a malformed stored value denies every host. A base URL never points at an admin host or at the host of the current request. `global_fetch_strictly_public` is enabled ([I-SSRF-1](docs/threat-model.md#i-ssrf-1)).
- Request records keep only claims on the profile's allowlist ([I-LOG-1](docs/threat-model.md#i-log-1)). Unverified claims are never stored ([I-LOG-2](docs/threat-model.md#i-log-2)). `tokengate-token` masks every token it prints ([I-LOG-1](docs/threat-model.md#i-log-1)).
- Every admin request is authenticated by its own Cloudflare Access JWT (team certs, exact issuer, application AUD). A suspension, role change or login reset applies to the user's next request, and admin writes re-check the acting identity and role when they commit ([I-SESS-1](docs/threat-model.md#i-sess-1)).
- Unsafe admin requests need `Sec-Fetch-Site` `same-origin` or `none` (without that header, an exact `Origin`) and a `_csrf` field equal to the `__Host-tokengate_csrf` cookie (double submit). Admin form bodies are capped at 64 KiB ([I-CSRF-1](docs/threat-model.md#i-csrf-1)).
- Email linking applies only to invited users and uses only the email of a valid Access JWT; an email that belongs to another user is refused ([I-LINK-1](docs/threat-model.md#i-link-1)). Bootstrap creates at most one owner, once, and stores the hostname of that sign-in as the first admin host ([I-BOOT-1](docs/threat-model.md#i-boot-1)).
- Every admin route has an RBAC entry ([I-RBAC-1](docs/threat-model.md#i-rbac-1)). Every admin change writes exactly one audit event in the same batch ([I-AUDIT-1](docs/threat-model.md#i-audit-1)). The last active owner cannot be demoted, suspended or deleted ([I-OWNER-1](docs/threat-model.md#i-owner-1)).
- `/admin` never answers on `workers.dev`. After the first sign-in, it answers only on the admin hosts in Settings, over https unless the host is a loopback host; a stored list that is not valid closes it everywhere. `wrangler.jsonc` sets `preview_urls: false` and `keep_vars: true`, and `apps/gateway/scripts/check-config.sh` enforces both ([I-DEPLOY-1](docs/threat-model.md#i-deploy-1)).
- A malformed configuration variable turns off the affected feature and is reported by name; no feature runs half-configured ([I-CFG-1](docs/threat-model.md#i-cfg-1)).
- `AUTH_ACCESS_DEVELOPMENT` together with `AUTH_ACCESS_TEAM_DOMAIN` or `AUTH_ACCESS_AUD` turns off both logins; the setup page names the error ([I-CFG-1](docs/threat-model.md#i-cfg-1)).
- The defaults in `.dev.vars.example`, which the Deploy button asks for, fail closed in production: the development login signs in no request through Cloudflare, and the development key is refused once Access is configured ([I-DEPLOY-1](docs/threat-model.md#i-deploy-1)).

### Upgrade notes

- This is the first release. There is no upgrade path from earlier development snapshots: deploy it into new D1 databases.
- Schema heads: `apps/gateway/migrations/0001_initial.sql` (`DB`) and `apps/gateway/migrations-telemetry/0001_initial.sql` (`TELEMETRY_DB`). `pnpm run deploy` applies both.
- The admin UI needs a custom domain behind an Access application. On a `workers.dev` hostname only `/proxy` and the health endpoints work. Sign in first on the custom domain: that hostname becomes the first admin host.
- `apps/gateway/wrangler.jsonc` declares no `vars`. Set operator variables in the Cloudflare dashboard; deploys keep them. See [docs/configuration.md](docs/configuration.md).
- Set `AUTH_ACCESS_TEAM_DOMAIN` and `AUTH_ACCESS_AUD` before you add services, and keep their exact values with the KEK. A later change requires every credential to be entered again ([docs/configuration.md](docs/configuration.md#login-binding)).
- The Deploy button asks for `TOKENGATE_KEK` and `AUTH_ACCESS_DEVELOPMENT`. Use your own KEK, and delete `AUTH_ACCESS_DEVELOPMENT` when you set the Access variables ([docs/getting-started.md](docs/getting-started.md#deploy-button)).
